# API записи: `201` с «голым» созданным ресурсом, серверная проверка слота и карта ошибок записи

Контракт записи — `POST /api/event-types` и `POST /api/bookings` — парный к
контракту чтения (ADR-0009) и держится на нескольких решениях.

- **Успех — `201` и «голый» созданный ресурс** в форме чтения: тип события —
  `{ id, title, description, durationMinutes }`, бронь — форма элемента
  `GET /api/bookings` (`{ id, eventTypeId, eventTypeTitle, start, end, guestName,
guestEmail }`). Фронт рисует экран успеха без повторного `GET`. Заголовок
  `Location` не ставим: `GET` одного типа события и `GET /api/bookings/:id` в
  контракте нет.
- **Тело создания типа события** — `{ title, description?, durationMinutes }`:
  `title` обязателен, `trim`, 1–100 символов, регистр сохраняется;
  `description` необязателен, `trim`, дефолт `""`, ≤ 500 символов;
  `durationMinutes` — целое, кратное 15, от 15 до длины рабочего окна
  (ADR-0003). Все нарушения — `400 VALIDATION_ERROR` с `fields`; отдельного кода
  для «не кратно 15» / «длиннее окна» нет — фронт зеркалит правило, бекенд
  источник истины. Уникальности `title` и лимита числа типов нет.
- **Тело создания брони** — `{ eventTypeId, start, guestName, guestEmail }`;
  `start` — строка `start` слота из `GET /api/event-types/:id/slots` (ISO 8601 со
  смещением зоны сервиса, ADR-0004); `end` сервер считает сам
  (`start + durationMinutes`). Гость не присылает `date` + `startTime`: это
  дублировало бы вывод сетки на клиенте.
- **Серверная проверка слота, по порядку**: (1) структура и поля тела →
  `400 VALIDATION_ERROR` (все невалидные поля сразу); (2) тип события существует
  → `404 EVENT_TYPE_NOT_FOUND`; (3) `start` — начало слота сетки этого типа
  (выравнивание от начала рабочего окна, слот целиком до конца окна) → иначе
  `400 INVALID_SLOT`; (4) локальная дата `start` внутри `today…today+13` → иначе
  `400 DATE_OUT_OF_WINDOW`; (5) `start > now` → иначе `400 INVALID_SLOT`;
  (6) транзакция (ADR-0007) → пересечение `409 CONFLICT`, `SQLITE_BUSY` после
  таймаута → `503 SERVICE_UNAVAILABLE`. Одно нарушение — один ответ: `400` и
  `404` вместе не возвращаются.
- **`INVALID_SLOT` и `DATE_OUT_OF_WINDOW` идут без `fields`**: это недоступность
  слота, а не ошибка поля формы — UI обновляет сетку, а не подсвечивает input.
- **`503 SERVICE_UNAVAILABLE`** — в конверте ADR-0005, без `fields` и без
  `Retry-After`: авторетраев нет, гость повторяет сам.

## Considered Options

- **`400 VALIDATION_ERROR` с `fields.eventTypeId` вместо `404` на неизвестный
  тип** — отброшено ради симметрии с чтением, где есть `EVENT_TYPE_NOT_FOUND`.
- **`200` вместо `201`** — отброшено: создаётся ресурс, `201` честнее.
- **`Location` на созданный ресурс** — отброшено: нет `GET` единичного ресурса.
- **Один код `SLOT_NOT_BOOKABLE` на все случаи недоступности** — отброшено:
  окно записи уже имеет код `DATE_OUT_OF_WINDOW` в чтении, дублировать его смысл
  новым кодом незачем.
- **`start` в `fields` при невалидном слоте** — отброшено: слот не поле формы,
  UI реагирует иначе (перезапрашивает сетку).
- **Присылать `date` + `startTime` вместо `start`** — отброшено: клиент
  дублировал бы вывод сетки.
- **`503 DB_BUSY`** — отброшено: код протекал бы реализацию (SQLite); наружу —
  про сервис.

## Consequences

- Карта ошибок записи дополняет ADR-0005 и ADR-0009: `400 VALIDATION_ERROR`
  (+`fields`), `400 INVALID_SLOT`, `400 DATE_OUT_OF_WINDOW`,
  `404 EVENT_TYPE_NOT_FOUND`, `409 CONFLICT`, `503 SERVICE_UNAVAILABLE`,
  `500 INTERNAL_ERROR`.
- Точные русские `message` не пиннятся — контракт и тесты бьют по `code`.
- Канонический вид контракта — TypeSpec (ADR-0008); `.tsp` пишется при
  реализации, а резолюция живёт в эпике #2 разделом «HTTP API → Запись».
- Проверка слота на бекенде повторяет вычисление сетки: сетка и валидация обязаны
  брать одни и те же рабочее окно и длительность, иначе валидный слот будет
  отвергнут. Соответствие проверяет контрактный тест (стратегия — #15).

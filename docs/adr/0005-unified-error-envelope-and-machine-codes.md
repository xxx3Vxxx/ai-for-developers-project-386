# Единый конверт 4xx-ошибок и машинные коды

API отдаёт ошибки клиента в одном формате — `{ error: { code, message, fields? } }`,
где `code` — стабильный машинный идентификатор на латинице (`SCREAMING_SNAKE_CASE`),
`message` — русское человекочитаемое сообщение, а необязательный `fields` — объект
«поле → сообщение» для ошибок валидации. Так клиент показывает `message` как есть,
тесты бьют по `code`, а форма брони подсвечивает конкретные поля. Валидация входа —
ручная функция-валидатор, возвращающая по-полевые сообщения; встроенную
schema-валидацию Fastify не используем, потому что её ответ на ошибку общий, а нам
нужен согласованный конверт и по-полевой вывод.

## Considered Options

Плоское тело (`{ message, fields }` без обёртки `error`) — отброшено: нет места под
машинный код, и сложнее расширять. Только машинные коды без текста — отброшено:
тогда русские тексты пришлось бы держать на фронтенде и дублировать в тестах.
По-полевые машинные коды (`fields.email.code`) — отброшены как избыточные для
учебного объёма.

## Consequences

Валидационные ошибки — `400` с `code: "VALIDATION_ERROR"`; конфликт брони — `409` с
`code: "CONFLICT"`. Возвращаются **все** невалидные поля сразу, по одному сообщению
на поле (приоритет внутри поля: `REQUIRED` → `TOO_LONG` → `INVALID_FORMAT`). Полную
карту остальных статусов (404, слот вне окна и т. п.) фиксирует контракт API записи.
Кто владеет русскими строками и когда их видно — ADR-0015; точные `message` и
по-полевые тексты — спецификация `#2`.

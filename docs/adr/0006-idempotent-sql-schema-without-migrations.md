# Схема создаётся идемпотентным SQL при старте, без миграций

База — SQLite (`better-sqlite3`), схема — две таблицы (`event_types`,
`bookings`), и изменение объёма не планируется: типы событий после создания
неизменяемы, брони не редактируются и не удаляются. Поэтому вместо фреймворка
миграций мы держим один SQL-модуль с `CREATE TABLE IF NOT EXISTS` и индексами и
применяем его идемпотентно при открытии базы (внутри `createDb()`), а вместе с ним
сеем предустановленные типы событий через `INSERT OR IGNORE`.

## Considered Options

Раннер миграций (версионированные SQL-файлы или библиотека вроде Kysely/Drizzle)
отброшен: при неизменной схеме он добавляет версионирование и служебную таблицу,
не окупая себя. ORM отброшен вместе с ним — запросов мало, они выражаются обычным
SQL, а `better-sqlite3` даёт синхронный API prepared statements.

## Consequences

Схема не эволюционирует: если объём изменится, миграции придётся вводить с нуля,
и первый шаг — сверить текущие таблицы с целевыми. In-memory база в тестах
создаётся тем же `createDb()` с `:memory:`, поэтому тестовая схема и сид не
расходятся с рантаймом.

# Экран /admin: рельс типов, форма создания в выдвижной панели, встречи — лентой по дням

Экран владельца календаря (`/admin`) — единственная админская поверхность
(ADR-0001, без авторизации) и решает две задачи: создать тип события и посмотреть
предстоящие встречи. Раскладка выбрана по прототипу из трёх структурно разных
вариантов (#12); отклонённые — ниже.

- **Типы событий — узкий левый рельс**, а не основное полотно: список читается как
  навигация (`название` + бейдж длительности), справочник не спорит с лентой за
  внимание. Создание типа в рельсе не живёт.
- **Форма создания типа — в выдвижной панели** справа, открывается кнопкой
  «Новый тип» в шапке страницы. На странице форма не показывается никогда, поэтому
  лента встреч получает всю ширину; панель — единственное место ввода.
  Поля — по ADR-0010: `title` (обязателен, 1–100), `description` (необязателен,
  ≤ 500), `durationMinutes` (кратно 15, от 15 до длины рабочего окна, ADR-0003).
  Ошибки валидации — под полями, панель остаётся открытой; успешное создание
  закрывает панель.
- **Предстоящие встречи — вертикальная лента, сгруппированная по календарным
  суткам зоны сервиса** (ADR-0004): заголовок дня («Сегодня», «Завтра», иначе
  «12 октября») и элементы с точкой на общей вертикали. Порядок — `start` asc,
  как в `GET /api/bookings` (ADR-0009). Элемент показывает `start–end`,
  длительность, название типа события, имя и email гостя — полный состав, который
  отдаёт контракт чтения.
- **Идущая прямо сейчас встреча выделена** маркером «идёт сейчас» и закрашенной
  точкой. Список строится по `end > now` (ADR-0009), поэтому текущий звонок в нём
  есть; без акцента он выглядел бы как любой будущий.
- **Пустое состояние** — текст на месте ленты («Пока нет предстоящих встреч»), а не
  пустая таблица; состояние ошибки чтения — алерт с «Повторить» на месте обеих
  областей; загрузка — скелеты.

## Considered Options

- **Две колонки: форма всегда слева, справа плотная таблица встреч** (вариант A
  прототипа) — отброшен: форма и таблица делят ширину, ни одна не получает
  достаточно места, а таблица из шести колонок хуже читается на узких экранах.
- **Одна колонка: типы строками с формой, раскрывающейся на месте, встречи —
  карточками по дням** (вариант B) — отброшен: инлайн-форма сдвигает содержимое
  при раскрытии, а карточка на каждую встречу избыточна для списка из
  «время + гость».
- **Рельс + выдвижная панель + лента** (вариант C) — выбран: справочник уходит в
  узкий рельс, ввод — в панель, лента встреч занимает всё оставшееся место.

## Consequences

- Экран читает `GET /api/event-types` и `GET /api/bookings`, пишет
  `POST /api/event-types` (ADR-0009, ADR-0010); фронт ничего не вычисляет сам,
  кроме форматирования и группировки по дням.
- **Редактирования и удаления типов событий нет** — сетка типа неизменна после
  создания (вне объёма карты #3); рельс только показывает типы.
- **Copy пиннится не здесь:** этот ADR фиксирует раскладку и состав областей;
  точные тексты — ADR-0015 и спецификация `#2`.
- Прототип с тремя вариантами и переключателем сохранён как первоисточник на
  ветке `prototype/admin-screen`; в `main` он не сливается. Реализация `/admin` по
  этому каркасу пойдёт отдельным тикетом.

# Ссылки на тикеты в коммитах и хук `commit-msg`

Связь «коммит ↔ тикет» держалась только комментариями внутри Issues, поэтому по
истории нельзя было понять, какой коммит закрывает какую задачу. Решаем сделать
ссылку на тикет **обязательной частью темы коммита** и проверять её хуком.

## Формат

- Тема — Conventional Commits (release-please, ADR-0005 не при чём; правила
  коммитов уже зафиксированы в `AGENTS.md`) плюс ссылка на тикет в конце:

  ```
  feat(backend): add booking endpoint (#29)
  ```

- Ссылка — GitHub-issue этого репозитория (`#N`); связь с тикетом даёт и запись в
  нём, и прогон CI.
- Служебные коммиты (`Merge`, `Revert`, `fixup!`, `squash!`) хук пропускает.

## Как проверяется

- Версионируемый хук `.githooks/commit-msg` проверяет две вещи: тему по шаблону
  Conventional Commits и наличие `#N`.
- Хук подключается из коробки: корневой `package.json` содержит
  `"prepare": "git config core.hooksPath .githooks"`, который выполняется на
  `npm install`/`npm ci`.
- История, накопленная до этого решения, переписана: темам коммитов добавлена
  ссылка на соответствующий тикет (реализация #22–#34, решения #4–#21, каркас и
  документация — #2).

## Considered Options

- **`commitlint` + `husky`** — отброшено: ради двух правил тянет зависимости и
  цепочку установки; `core.hooksPath` на версионируемый каталог делает то же без
  пакетов.
- **CI-проверка сообщений вместо локального хука** — отброшено: ошибка всплывает
  уже после push; хук ловит её на этапе коммита, а CI при желании можно добавить
  позже.
- **Только конвенция без проверки** — отброшено: ровно так ссылки и потерялись.

## Consequences

- Полезная нагрузка приходит в PR и CI: задача и коммит связаны явно.
- Хук локальный и его можно обойти (`--no-verify`), поэтому дисциплина остаётся за
  автором; при необходимости добавим проверку в CI.
- Переписывание истории потребовало force-push основных веток; release-please
  стартует заново от новой истории.

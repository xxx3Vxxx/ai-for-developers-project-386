# Конфигурация — через env, единый модуль, fail-fast

Вся настройка сервиса приходит **только из переменных окружения**, читается **один
раз при старте** в одном модуле `backend/src/config.ts` функцией
`loadConfig(env = process.env)`, которая возвращает замороженный типизированный
объект. Дефолт применяется **только когда переменная не задана**; заданное
некорректное значение — это ошибка запуска: `loadConfig` бросает, `server.ts`
логирует и делает `process.exit(1)`, называя переменную и ожидаемый формат. Тихих
откатов к дефолту нет.

Набор переменных (без префикса, продолжая уже существующие `PORT`/`HOST`/
`SERVICE_TIMEZONE`):

| Переменная             | Дефолт                 | Значение                                                         |
| ---------------------- | ---------------------- | ---------------------------------------------------------------- |
| `PORT`                 | `3000`                 | целое 1–65535                                                     |
| `HOST`                 | `0.0.0.0`              | непустая строка                                                   |
| `DATABASE_PATH`        | `./data/calendar.sqlite` | непустой путь к файлу SQLite; каталог создаётся при старте     |
| `SERVICE_TIMEZONE`     | `Europe/Moscow`        | валидная IANA-зона (проверка через `Intl`)                        |
| `WORK_DAY_START`       | `09:00`                | `HH:MM` (24 ч), `start < end`                                     |
| `WORK_DAY_END`         | `18:00`                | `HH:MM` (24 ч)                                                    |
| `BOOKING_WINDOW_DAYS`  | `14`                   | целое 1–365 (верхняя граница — защита от опечатки)                |

Конфиг **инъектируется** в приложение: `buildApp({ config })` с дефолтом
`loadConfig()`, поэтому тесты передают свой объект и не трогают `process.env`.
Файлы `.env` не подхватываются: `dotenv` не используем, в репозитории лежит
коммитнутый `.env.example` со всеми переменными и дефолтами плюс таблица в
`README.md`.

## Considered Options

`dotenv` — отброшен: лишняя зависимость, а реальные окружения (CI, контейнер) задают
переменные напрямую; `.env.example` закрывает вопрос локального удобства.
Откат к дефолту с предупреждением при некорректном значении — отброшен: молчаливая
подмена `PORT=abc` на `3000` даёт сервис, работающий «не там», и это дороже упавшего
старта. Префикс (`CALENDAR_*`) — отброшен: `PORT`/`HOST`/`SERVICE_TIMEZONE` уже
зафиксированы без префикса, вводить его частично хуже, чем не вводить вовсе.
Чтение `process.env` по месту в роутах — отброшено: конфиг нельзя подменить в тестах,
а разбор и валидация размазываются по коду.

## Consequences

Некорректная конфигурация валит процесс на старте — это ожидаемое поведение, а не
баг. Тесты бекенда получают конфиг инъекцией, поэтому не зависят от окружения.
Упаковка и запуск (#17) опираются на `DATABASE_PATH` как на единственную точку
переопределения места хранения (в контейнере — том/путь монтирования) и на `PORT`
для прослушивания порта. `PORT` и `HOST` читаются в `server.ts`, а не в общем
модуле, но разбираются и валидируются тем же `loadConfig()`.
